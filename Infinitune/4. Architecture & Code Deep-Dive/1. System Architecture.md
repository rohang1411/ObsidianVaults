

The InfiniTune framework is built on a decoupled, three-component architecture. These components operate independently and communicate using [[2. Apache Kafka]] as a streaming message bus.

## 1. Component Breakdown

The system is divided into three core services:

1.  **Data Generator (`producer.py`)**
    * This is a [[1. Pub-Sub Model (Publish-Subscribe Model)|Kafka Producer]].
    * **Purpose:** Its sole responsibility is to ingest data from a source (e.g., the IMDB review corpus) and stream it, sample by sample, into the first Kafka topic ("training_data").
    * It's configured to handle various textual datasets and includes delays to prevent overloading the GPU on the trainer.

2.  **QLORA Trainer (`trainer.py`)**
    * This is both a Kafka Consumer and Producer.
    * **Purpose (Consume):** It subscribes to the "training_data" topic, consuming the live data stream.
    * **Purpose (Train):** It aggregates these data samples into mini-batches and performs continuous [[2. Online Learning (ML)|online fine-tuning]] using the [[4. QLoRA]] technique.
    * **Purpose (Produce):** After a set training interval (e.g., 60 seconds), it automatically captures the newly updated [[3. LoRA (Low-Rank Adaptation)|LoRA]] adapter weights and publishes them as a new message to the *second* Kafka topic ("lora_weights").

3.  **Inference Server (`inference_api.py`)**
    * This is a Kafka Consumer and a [[1. Flask]] API server.
    * **Purpose (Serve):** It runs a live [[1. Flask]] API endpoint that users can query to get responses from the [[1. Large Language Models (LLMs)|LLM]].
    * **Purpose (Consume):** It runs a background thread that subscribes to the "lora_weights" topic.
    * **Purpose (Hot-Swap):** When new adapter weights arrive, this thread loads them and "hot-swaps" them directly into the live model's state. This updates the model's knowledge *in real-time* with no downtime.

## 2. The Data Flow

The entire system relies on a two-topic Kafka design to decouple the training process from the inference service.

**Flow 1: Training Data**
1.  `Data Generator` reads a sample from the IMDB dataset.
2.  Publishes the sample to Kafka **Topic A: `training_data`**.
3.  `QLORA Trainer` consumes the sample from **Topic A**.
4.  The trainer uses the sample to update its local [[3. LoRA (Low-Rank Adaptation)|LoRA]] weights.

**Flow 2: Model Weight Updates**
1.  After 60 seconds, the `QLORA Trainer` packages its updated [[3. LoRA (Low-Rank Adaptation)|LoRA]] weights.
2.  Publishes these weights as a single message to Kafka **Topic B: `lora_weights`**.
3.  The `Inference Server` (and any other replicas) consumes the weight update from **Topic B**.
4.  The `Inference Server` immediately applies these weights to its live model.
